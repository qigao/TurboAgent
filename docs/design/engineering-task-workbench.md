## 1. 产品定位与首批场景

用户给出工程目标，工作台组织资料、形成可调整的计划、在现有授权内执行，
最后交付变更和验证证据。每次交付要回答：依据是什么、做了什么、验证了什么、
还有什么不确定。

首批用户是维护代码和工程资料的开发者，以及希望在原生软件内接入 Agent 的宿主开发者。
第一版以单用户、本地工作区和显式接入的资料为范围。

| 场景 | 用户得到的结果 | 首次交付阶段 |
| --- | --- | --- |
| “结合代码和这份测试日志，解释失败原因” | 带来源、版本和不确定项的诊断建议；用户能检查依据 | M0 只读资料与证据 |
| “按这个目标执行一次只读检查” | 可检查的提案、已准入的 Inspect、可追踪的执行结果 | M1 单步任务 |
| “修复问题并验证” | 修改提案、实际 diff、测试结果、未完成项；失败可定位到具体尝试 | M2 Change/Repair |
| “完成一次构建和交付准备” | 经审查流程的阶段结果及交付清单 | M3 多阶段流程 |

代码依赖分析、CI 服务接入和业务系统操作分别需要明确适配器。首个切片使用用户选择的
代码、文档和日志快照，不假设能自动查询任意外部服务。发布准备的完成不授予发布权限。

| --- | --- | --- |

| 工作流 | 有限 DAG、Change/Repair、可选 Praktor、受限 CMeta/CFlow 原生区域 | 任务阶段、验收条件与 backend 明确对应 |
| 执行证据 | Run/Checkpoint、Tool Journal、Inspect 原子 attempt 和唯一持久结果 | 任务对证据的引用、交付判定和失败解释 |
| 可视化 | 已有文档、计划、运行与工具证据的 JSON/Mermaid 投影 | 目标/计划/证据/结果的连贯界面；图按需展开 |

日常 CLI 默认仍执行模型/工具循环；新工作台不得将这些调用自动标记为 compiler-qualified。
当前 Harness compiled Inspect 是显式、同步、只读切片，不是通用异步 DAG 执行服务。

稳定的构建/测试片段按 [Skill 与 YAML 工作流能力包设计](skill-workflow-packages.md)交付：
Skill 负责诊断和选择参数，Host 注册准确版本的工具；可选 Praktor 承担已审查的固定流程。
M2 先核对实际验证结果，M3 再扩展多阶段生命周期；不以 YAML 固定步骤推导未知副作用可安全重跑。

## 3. 用户流程与界面

用户首先输入目标和完成条件，选择工作区与资料。工作台展示找到的依据、来源版本和缺口，
再展示步骤、预计影响范围和验证方式。用户可以调整目标、资料和提案；已经授权且未越界的
普通步骤按既有授权继续执行，不要求逐步重复确认。

界面优先显示四类内容：

- **任务**：目标、完成条件、当前阶段、阻塞项及下一步。
- **提案**：计划版本、每步输入/输出、将访问或改变的对象、验证方式。
- **证据**：来源及其版本、工具结果、测试记录、引用位置、新鲜度和缺失信息。
- **交付**：实际变更、通过/失败/未执行的验证、残余风险及可选择的后续动作。

执行细节、依赖图和原始诊断按需查看。用户入口采用业务表达，例如“查看依据”“修改提案”
“开始已授权任务”“取消”“查看失败原因”；内部 collection、generation 和 backend 配置不进入
普通操作流程。第一版可以使用 CLI 的有界 JSON/Mermaid 输出，不以完整 TUI 为前置条件。

“暂停”只能发生在已定义的边界；任意工具内部挂起、持久定时器和外部等待不是已有承诺。
取消后显示已知结果和可能发生的副作用。新的明确重试保留历史并取得新尝试身份，不能清空
失败标记后自动重新执行未知操作。

## 4. 数据与模块归属

| 对象 | 权威来源/所有者 | 设计规则 |
| --- | --- | --- |
| SourceRevision / EvidenceRef | 实际资料源；KnowledgeStore 保存已索引快照 | 引用包含来源身份、内容摘要、精确定位和快照范围；URI/行号不充当稳定符号身份 |
| 关系视图 | 独立、可重建的 SQLite sidecar 索引 | 边保留关系类型、来源版本、提取器版本及直接观察/推断标记；不拥有源内容或执行状态 |
| Job / ProposalVersion | 未来 Agent/Harness 任务协调层 | 拥有目标、完成条件、不可变提案版本和生命周期；用户修改是持久记录，不随索引重建丢失 |
| ExecutablePlan / Certificate | AgentCompiler，消费 RuntimeTools 和 Host 授权 | 冻结准入事实；提案和图中的关联均不能授予执行权限 |
| Run / Checkpoint / Tool outcome | 现有 Runtime 和执行路径 | 任务引用现有记录；不得复制另一份可独立改写的持久工具结果 |
| Approval / Grant binding | Host 决策；任务层保存准确的绑定记录 | 记录授权范围和准入时依据，不能从模型文本或图边推断授权 |
| UI / 报告 | 上述对象的查询投影 | 不成为新的调度器、结果权威或可独立写入的会话状态 |

Runtime 保持独立于知识索引和工作台语义；协调层组合公开接口。复用现有 Salts/CMeta 的
原生类型与生命周期契约、SaltsUtils IDL/DataBind 的已安装生成能力，以及已有文件/进程 owner，
不另外建立反射、序列化、进程或 workflow 执行器。

M0 只导入明确选定且可核对版本的快照，关系索引独立持有连接和事务。
索引和会话的持久写入来自 Host 明确配置的存储授权；只读限制约束模型暴露的工程工具，
不把获准的索引导入冒充为零存储 I/O。
不通过旁路连接在 Runtime SQLite 文件中加表。一次索引批次成功后才发布新 generation；失败保留
上一批并显式标记陈旧。来源更新、删除、重命名、未扫描范围均可见，不宣称实时全仓同步。

M1 实施前必须定义版本化 Job 记录、准入规则、发布顺序和迁移/回滚方案。优先通过现有
RuntimeStore 记录接口保存 Agent 拥有的记录；其单条原子 claim 不等于跨记录事务或崩溃持久性。
一个 Job 协调 owner 串行化生命周期变化；不支持的多写者/CAS/持久语义应明确拒绝。
计划、任务头和运行记录之间的故障窗口要有恢复规则，不能把“最后写一个 head”描述为多记录原子提交。

## 5. 执行、审查与交付契约

每个提案版本固定目标、源版本、步骤、工具/Provider 身份、规范参数、效果、资源范围和完成条件。
审查记录绑定这些准确内容及现有 grant；现有 64-bit plan hash 是身份辅助，不能单独成为
防篡改授权凭证。绑定记录保留规范证书和准确字段，修改内容后重新评估授权。

执行前检查当前授权、来源前提和计划身份。来源改变时返回陈旧提案或重新规划；修改生成新版本，
不能原地改写运行中的计划。预检摘要不保证整个工作区的原子快照；写工具需要在自身支持的提交边界
执行相应冲突检查，无法提供的并发保证必须明确披露。

策略替换保持现有 quiescent 契约：等待执行和回调结束后由 Host 串行更新。
generation 只负责失效，不能用于推导执行期间修改普通策略字段安全，也不能在工具/存储/事件回调里调用 setter。

| 情况 | 工作台行为 |
| --- | --- |
| 参数、工具、能力或效果未准入 | 不进入工具；报告拒绝原因，无旧路径隐式 fallback |
| attempt 已提交且身份/授权仍匹配 | 引用和交付既有规范结果；不再次进入回调 |
| attempt 为 STARTED 或结果不确定 | 显示需核对状态；不自动重新执行 |
| 工具返回但验证失败或证据不足 | 显示未完成/验证失败，保留真实结果和已有变更 |
| 提交后报告/界面交付失败 | 从同一结果权威恢复交付；不得重新产生副作用 |
| 取消或超时 | 等待所属 owner 的取消/drain 协议；结果中保留可能已发生的副作用 |

工具成功只是一条证据。Job 达到完成条件才显示完成；测试被跳过或未运行必须保持不同状态。
回滚只用于工具明确支持的补偿动作，不能承诺任意外部操作可撤销。跨 backend 的保证必须逐项测量。

## 6. 交付阶段与退出标准

| 阶段 | 可交付能力 | 退出标准 |
| --- | --- | --- |
| M0 只读资料与证据 | 查找选定资料、查看直接关系与引用、解释已知证据和缺口 | 离线夹具通过来源/版本/新鲜度/有界查询验证；无写入和进程工具调用；索引可重建 |
| M1 可检查的单步任务 | 目标与完成条件、不可变提案、一个已授权 compiled Inspect、任务与现有 attempt 关联 | Job schema/发布恢复设计完成；陈旧来源/授权拒绝；提交后恢复交付不重复回调；不引入第二份结果 |
| M2 工程 Change/Repair | 精确变更提案、必要的 Host 审批、实际编辑/测试和验收报告 | #72/#73/#74/#77 对应路径准入、权限、未知副作用、故障注入及恢复门禁通过；Windows shell 需满足 #193 |
| M3 多阶段流程 | 经审查的构建/验证宏工具、阶段依赖和有限子任务 | 明确 backend 能力、阶段身份、资源/重规划预算、跨进程恢复与取消；Praktor 保持可选 |
| M4 可选扩展 | 分层模型路由、更多应用适配器、动态 Provider 或语音入口 | 每个扩展有独立协议、生命周期、质量和平台验收；不作为 M0–M2 的前置条件 |

这些阶段按退出标准推进，不根据累计 PR 数、CI 变绿次数或未经测量的日期判定完成。
M0 不依赖完整代码语义图、动态 Plugin、真实模型、语音或跨系统事务。
M1 不因 Inspect 成功而开放写入；M2 不因旧 DAG/backend 测试通过而假定 Harness 全路径已集成。

## 7. 首个实施切片：M0

输入为一个选定代码文件、两份相关说明、一份用户提供的失败日志和一组明确选择的已有运行记录。
先用现有知识查询和证据投影生成一个有界视图，支持“找到资料—查看直接关联—解释依据”。
关系只接受明确的 contains、字面 URI 引用和已有 plan/run/tool 记录引用；calls、语义 documents、
完整依赖影响分析等需要专门提取器的边不进入第一版。没有依据时返回未建立关系，不能猜测依赖不存在。

实施顺序：

1. 固定这个场景的输入/输出夹具、来源版本和用户可见结果，并核对现有 CLI/SDK 能力。
2. 在 Agent 查询/投影层组合知识和执行证据；Runtime 不反向依赖知识或 Compiler。
3. 只有需要持久关系时加入独立 sidecar；保留 schema 版本、来源范围和发布 generation。
4. 暴露有界 JSON 与现有 Mermaid 投影入口，原有聊天/编程命令行为不变。
5. 再接入模型生成建议；建议必须带实际可解析的引用。先用离线注入 Provider 验证，真实模型评估单独执行。

所有入口声明字节、条目、深度、节点/边、候选和耗时预算；复用已有查询/diagram 限制，
超限显式失败或按已定义协议披露截断，不能静默扫描超过 RuntimeStore 的 list 范围。
离线夹具至少验证：

- 返回的引用准确对应选定来源和内容版本；模型生成的无效引用不能冒充真实证据。
- 来源变化、删除、重命名歧义、缺失记录及过期索引可见；失败批次不覆盖已发布视图。
- 循环关系、过深查询、超量输入、非法 URI/记录和部分导入受限，失败不交付伪完整结果。
- 结果只包含需要的证据，支持逐项查看来源；界面不把测试未执行显示为通过。
- 模型或资料中的指令不能扩大授权；只读场景没有写入/进程回调。
- 重建索引不修改源文件、不删除用户提案，也不改变 Runtime 的执行证据。

## 8. 指标与验收证据

产品评估使用固定任务集并保留样本数、任务类型、源版本和人工核对记录；暂不承诺精度或性能提升。

| 维度 | 测量内容 |
| --- | --- |
| 证据质量 | 引用可解析率、来源版本匹配、错误/缺失引用、人工核对后保留的建议 |
| 任务完成 | 独立验证后的成功/部分完成/失败，用户修改次数，重新规划原因 |
| 执行可靠性 | 越权回调数、重复效果准入、故障后结果一致性、未决副作用是否准确暴露 |
| 使用成本 | 检索/规划/执行分别的耗时、模型 token/费用（有可靠 usage 时）、索引大小与峰值内存 |
| 用户控制 | 能否定位依据、理解将发生的变更、取消并查看实际结果、选择新的后续尝试 |

离线行为测试、实际模型质量测试、installed SDK、sanitizer 和设备运行记录分别报告。
源码/ABI 改动执行对应平台和消费者门禁；文档-only 变更核对链接和事实，不以构建结果声称产品已实现。

## 10. 迁移与后续选择

M0 采用新增查询投影和独立索引；禁用工作台或删除可重建索引可回退到现有 CLI/SDK，
源资料和执行记录保留。M1 的 Job/审查记录是权威用户数据，须在实现前设计 schema、
迁移、兼容拒绝和可恢复的回退方式，不能当缓存随意删除。公共 API 只有在对应切片实现和
测试后才成为承诺；本文的领域名不是已经导出的 C API。

后续业务助手和原生软件集成复用同一任务/证据/授权接口，由各宿主提供业务工具。
通用 Agent 的开箱体验、记忆管理、连接器/调度和模型 Router 按双路线规划独立交付，
不以工程 M0–M4 全部完成为前提，也不因其工程阶段标签而被整体延后。
智能模型路由、完整 UI、实时同步、语义代码图、任意长时外部等待和真实语音均按独立需求推进。
先验证“带来源的只读分析”，再验证“有证据的一次执行”，最后扩展可组合的工程流程。
