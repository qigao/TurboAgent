# Skill 与 YAML 工作流能力包：执行设计与首批交付

状态：设计提案，2026-10-22。事实基线为 main
`d4897c0ac063494a63878b4e51d3453ef2e1894c`。本提案服务于
[通用 Agent 与工程工作台两条路线](agent-product-roadmap.md)，不新增已实现的包格式、
Skill frontmatter 字段、公共 ABI、存储格式或线程安全保证。

## 1. 决策与适用范围

将稳定、重复且可独立验证的执行片段组织为可审查的能力包：Skill 负责适用场景、
参数收集、领域方法和交付标准，已注册的工具负责执行；需要固定多步骤时，用既有
Praktor YAML 工作流作为可选宏工具后端。模型保留理解目标、处理未知情况和重新规划的职责。

优先采用现有工具注册、契约校验和执行 owner，不建立第二套 YAML 解释器、调度器或结果数据库。
纯指令 Skill、单个原生工具、Wasm 工具和其他已支持后端仍可独立使用；不要求每个 Skill 都配 YAML。
工作流只有执行结构固定，外部服务、进程和文件内容仍可能变化，不能据此承诺结果确定或效果只发生一次。

候选方案及取舍：

| 方案 | 适用情况 | 本规划的选择 |
| --- | --- | --- |
| 模型逐步编排普通工具 | 新问题、步骤尚未稳定、探索与诊断 | 保留；稳定片段可逐步沉淀为能力包 |
| Skill 选择注册工具，固定流程作为宏工具 | 重复文档加工、构建/验证、受控业务流程 | 首选组合；增加版本审查和夹具维护成本，收益须测量 |
| Skill 内任意路径/脚本自动执行，或新建通用 DSL | 需要另行设计执行与权限体系 | 不纳入；当前工具注册和可选 Praktor 已提供复用入口 |

## 2. 当前事实与待补齐部分

| 当前事实 | 对能力包设计的约束 |
| --- | --- |
| [Workspace Skills](../../agent/docs/workspace-skills-tools.md) 通过 `tools` 和 `capabilities` 选择注册工具，Markdown 不是回调 | Skill 不能凭文件存在取得执行权；当前没有工作流路径自动绑定字段 |
| CLI `--workflow loop\|review\|engineering` 选择 Session preset | 该选项不表示加载某个 YAML 能力包 |
| [PraktorTools](../../praktor_tools/README.md) 支持 Host 注册稳定工具名，模型不提供 workflow path | YAML 的发现、审查与注册属于 Host；模型只提交已注册工具名和参数 |
| WorkflowPlan-capable SDK 可生成输入 schema、检查 harness-safe profile、绑定依赖摘要并派生效果要求 | 新包的严格工作流 profile 要求这些能力，不能只凭 YAML 文件名认定已准入 |
| 旧 SDK/配置仍存在 reviewed-path 兼容路径 | 新包 profile 必须显式检查支持度；不能宣称现有适配器全面无 fallback |
| [AgentCompiler 边界](../../agent_compiler/BOUNDARY.md) 只适用于显式 compiled 路径 | 普通循环中的宏工具调用不能自动标记为 compiler-qualified |
| [Harness compiled Inspect](../../harness/include/turbo_agent_harness.h) 是同步单步只读切片 | 多步骤写流程、持久审批和跨进程恢复须分别接入与验收 |

当前 general CLI 使用空工具注册表。第一批文档场景先返回有界内容，再由用户明确的 Host 导出动作保存；
增加文档宏工具的注册是独立实现任务，不能靠选中 Skill 默认扩大 general 模式权限。

## 3. 能力包内容与契约归属

以下是提议的逻辑组成，尚未规定磁盘 manifest 文件名或新增解析语法。
首个实现 PR 需先固定版本化 manifest schema、解析上限和兼容拒绝规则，再加入加载入口。

| 组成 | 内容与所有者 |
| --- | --- |
| Skill 说明 | 适用条件、需询问的输入、方法、失败处理、交付标准；沿用已支持的 frontmatter |
| 工具绑定清单 | 包身份/版本、稳定工具身份、后端及最低能力、契约和审查内容的引用；由 Host 准入 |
| 可选工作流 | 经审查的有限步骤、依赖、显式输出；复用 Praktor 的已有语法和 runner |
| 输入/输出契约 | 一个规范定义，其他部分引用或生成；工作流输入优先消费 WorkflowPlan 生成 schema |
| 验证器 | 结构检查和领域完成条件，明确版本、资源范围、效果和预算；作为普通获准工具执行 |
| 离线夹具 | 正常输入、边界、拒绝、失败、取消、版本变化及交付样例；不以模型自评替代验证 |

不在 Skill、manifest、YAML 和 C 代码中手工维护四份参数 schema。
复用 RuntimeTools 的规范工具契约与 schema validator；涉及原生类型和生成时复用已安装的
Salts/CMeta 与 SaltsUtils IDL/DataBind 能力。遇到不支持的必要 schema 语义明确拒绝，不能猜测通过。
凭据由 Host 的既有凭据 owner 管理，不写入能力包或模型可见参数。

包身份需要区分稳定名称、发布版本和内容身份。审查绑定至少包含 Skill 指令、工作流根及传递依赖、
规范契约、验证器、工具实现/构建身份、后端能力和必要配置；运行证据引用这些绑定。
内容摘要用于发现变化，不能代替来源信任或 Host 授权；不只用当前 64-bit plan hash 充当防篡改凭证。

## 4. 准入与执行路径

1. Host 在安全点发现有界包内容，核对来源、版本、依赖与 backend 能力，拒绝未知必需字段和不支持的 profile。
2. Host 注册准确的工具定义；工作流 profile 显式检查 WorkflowPlan 支持度并要求 harness-safe qualification。
   不支持时该包不可用，不能依赖适配器的旧 SDK 兼容行为继续执行。
3. Workspace 根据 Skill 和当前 grant 生成工具投影；模型选择已暴露的工具名，提交符合 schema 的结构化参数。
   模型不提交 workflow path、任意插件路径或拼接后的 shell 命令。
4. 所选执行路径检查参数、当前授权、资源范围、版本绑定和预算。显式 compiled 路径另行冻结工具与参数并准入，
   准入失败返回诊断；需要重规划时产生新的源计划和新准入，不隐式进入普通循环执行。
5. 既有执行 owner 调用绑定后端，传播取消、deadline 和 lineage；验证器检查实际输出，交付带证据的结果。

包声明的是要求，Host grant 才是权限来源。要求取包/工具/工作流派生效果与 Host 附加要求的并集，
每一项均须获准；Skill 选择、参数文本和子 Agent 不能扩大 grant。资源范围也须满足 Host 的实际约束。
原生或 shell 回调的实际效果不能仅靠模型声明或工具名推导，须由可信实现和对应 backend 契约保证。
`shell` 等能力位不等于路径隔离或硬进程沙箱。

首版包不接受任意 shell 字符串。对命令型后端只开放已审查 preset/枚举和受限参数，优先复用结构化
HostTool 调用；参数传递须按目标进程接口处理，不能把 schema 合法误认为 shell 插值安全。
原生、Wasm、MCP 与 Praktor 只共享可共同证明的语义；缺少必需的限制或恢复能力时拒绝对应 profile，
不把“一份 Skill”解释为所有后端自动等价。

所有包有文件数/总字节/依赖深度、输入输出字节、步骤/扇出、耗时和重试预算。
具体值由首个实现 profile 固定并验证，超限显式失败。首版固定流程不隐藏模型循环；
语义失败返回可供 Agent 重规划的诊断，不在 YAML 内无限修复或切换后端。

## 5. 生命周期、审批与版本变化

已有 grant 内且绑定未变的操作连续执行，无需逐步重复确认。需要 Host 决策的操作绑定准确参数、
源版本、工具/验证器/工作流身份、效果和目标范围；提案修改形成新版本，并重新评估授权。
仅显示“批准了这个 Skill”不足以授权之后变化的流程或任意参数。

工作流文件及依赖使用 WorkflowPlan 已支持的摘要检查；工具实现和验证器的生命周期由各自 owner 保证。
重查文件摘要不提供整个工作区的原子快照，也不能检测外部服务状态全部变化。
写工具仍需在自身提交边界检查相应前提；无法保证的部分明示。

注册表、借用的回调依赖、包绑定和策略在执行及结果交付期间保持稳定。
刷新先等待相关执行/回调 drain，在 quiescent 点构建替换；失败保留上一份已发布视图。
`turbo_agent_set_tool_policy()` 仍是 quiescent 控制面操作；generation 使旧授权绑定失效，
不提供普通策略字段的并发读写同步，也不能在工具、存储或事件回调中调用 setter。
首版不要求热更新；不增加运行中策略替换的线程安全承诺。

## 6. 失败恢复与结果验证

任务协调层引用既有规范执行结果和 attempt，不另存一份可独立改写的工具结果。
Praktor runner 的内部阶段状态与 Harness/Runtime 的规范工具结果职责分开；内部状态只有通过
已验收的身份、提交和恢复协议才能用于恢复，不能凭工作流名推导整个流程可安全重跑。

| 情况 | 预期行为与验收证据 |
| --- | --- |
| 参数、版本、能力或前提不匹配 | 在相应执行准入边界拒绝；拒绝前不进入效果回调 |
| 输出结构错误或领域验证失败 | 保留真实执行结果与已发生效果；任务显示验证失败/未完成 |
| 验证器超时、缺失或未执行 | 与验证通过区分；不能把工具 exit code 0 当作完整任务成功 |
| 规范结果已提交，报告/界面交付失败 | 重试交付时引用同一结果，权限仍需有效；不再次进入效果回调 |
| STARTED、崩溃或外部效果不明 | 保留未知状态并阻塞自动重派；核对/补偿/新尝试需对应工具协议 |
| 取消或超时 | 遵守 backend 取消与 drain；列出已完成和未知步骤，取消不代表回滚 |

以上是包 profile 的目标，需在对应执行路径实现并验证。当前 Harness 对 compiled Inspect 的
同一 attempt 重放要求计划/契约和 Host policy generation 匹配，且 STARTED/未知 attempt 不自动重派；
不能把这个单步保证外推到任意普通宏工具或多步骤写流程。RuntimeStore 单条原子操作不提供跨记录事务。
未完成这些门禁的包只交付明确范围内的能力，不宣称持久恢复或端到端 exactly-once。

验证器先检查结构和范围，再核对领域条件。模型摘要与完整证据分开：摘要用于后续推理，
完整工具输出和诊断沿既有 detail sink/journal 保存并引用。通用任务可核对引用、格式和内容覆盖，
工程任务需报告实际目标、退出状态、用例、跳过项和来源版本；主观内容质量仍需要固定样例与人工评估。

## 7. 两条路线的首批能力包

下列工具名称为候选名称，尚未注册或公开。

| 内容 | 通用：`document_render` | 工程：`build_test` |
| --- | --- | --- |
| Skill 负责 | 理解资料与写作目标、组织草稿、解释缺口 | 理解失败、选择已支持 preset、提出修复或后续验证 |
| 输入 | 有界草稿、精确来源引用、受支持格式/模板 | 已审查 preset/目标、源版本前提和预算；不接受任意命令 |
| 固定执行片段 | 校验输入与引用、模板渲染、解析输出及格式检查 | 检查源前提、构建、测试、收集结构化结果 |
| 初始交付 | 有界 Markdown 内容和引用检查结果，保存通过明确 Host 导出 | 实际构建/测试状态、日志引用、用例和跳过项；不发布产物 |
| 验证重点 | 无效引用/超量输入拒绝，内容与格式可核对，导出失败可见 | 构建失败不报成功、未执行测试不报通过、取消和未知步骤可见 |
| 路线位置 | G0 的受控文档能力；任务持久化消费 G1 | M2 的工程验证片段，M3 再接多阶段生命周期 |

通用包先证明现有原生工具组合也能满足契约，不为单个模板强制引入 Praktor；
确有重复步骤时再用可选 YAML 宏工具。工程包依赖实际构建工具、process owner 和平台行为，
Windows shell 相关验收继续受 #193 约束。两个包均不阻塞 G0/M0 的只读切片。

## 8. 实施顺序、评估与回退

1. 分别固定两个场景的输入、预期交付和拒绝/失败夹具；核对现有模块可直接组合的部分。
2. 先用一个 Host 显式注册的有界文档工具验证 Skill 投影、参数和结果契约，不先实现目录自动安装。
   若需要持久包记录，先定义 schema/迁移；公共 API 变更随对应实现审查。
3. 在独立 PR 中实现版本化绑定与严格 profile 准入，用 fake 工具/后端验证零效果拒绝、内容变化和生命周期；
   不能靠扫描源码标记证明准入行为。
4. 另行接入可选 Praktor 工作流包及工程夹具，按实际入口验证执行前、重放和交付阶段权限，
   加入失败/取消/未知效果和 backend conformance 门禁；普通循环与 compiled 路径分别报告。
5. 需要后台持续任务、审批等待或子 Agent 时，消费 G1/G2/G3 与 M1/M3 的已验收协调能力，
   不在能力包中新增隐蔽的持久任务服务。

权限/后端/恢复/精确审批分别关联 #72/#73/#74/#77 的实际责任；子任务监督与 Router 仍归 #213。
不把所有跟踪项关闭作为每个只读包的前提，也不借一个包的通过替其他执行模式收口。

评估在相同任务、模型、授权和完成条件下比较“模型逐步编排”与“调用固定流程”：
记录独立验证后的成功率、模型轮次/token、执行及验证耗时、人工修正、重复效果和故障后的实际状态。
分别报告离线行为与真实模型质量，不预设更快、更省或成功率更高。

本阶段只增加设计文档。后续禁用某个包时停止新准入，等待依赖 drain 后释放；保留历史版本及证据引用。
现有纯指令 Skill、工具注册和 CLI preset 继续按原契约使用。若新包 profile 无法满足，显式不可用；
不能以回退旧版本之名重新执行有未知效果的 attempt。本提案不启动安装、付费模型、发布或自动合并。
